## Context (read first)

This continues the **already-shipped** right-docked chat panel (markdown rendering,
attach-to-import, `useAgentChat` refactor). That work is on the branch and green. This spec
covers five **follow-up** improvements to the same chat panel + agent loop, driven by owner
feedback while testing it live. It is self-contained — assume no prior conversation.

**What already exists (files you will touch or reuse):**
- `src/app/components/agent/AgentWidget.tsx` — owns the chat state (`useAgentChat`), renders
  the right-docked panel + launcher. Panel is always mounted, slides off-screen when closed.
- `src/app/components/agent/ChatPanel.tsx` — presentational: header (sparkle tile +
  "Wealthwise Advisor" + **new-chat** + minimize), message bubbles, `<Affordances/>`, input
  row (attach + text + send), empty state, `Bubble`/`TypingDots`/`EmptyState` subcomponents.
- `src/app/components/agent/Affordances.tsx` — renders confirm cards, select/multiselect,
  account_picker, and tokenless suggestion chips. **Currently styled with ad-hoc classes**
  (`rounded border`, `bg-black/80 text-white`) — not the app's Origin tokens.
- `src/app/components/agent/MarkdownMessage.tsx` — GFM markdown renderer (safe links, no raw
  HTML). Reuse for assistant text; optionally for reasoning text.
- `src/app/hooks/useAgentChat.ts` — SSE hook. `ChatMessage = { role, text }`. `consume()`
  dispatches SSE frames: `conversation`, `text`, `proposal`, `error`. It **ignores**
  `thinking`, `tool_start`, and `done` frames today. Exposes
  `{ messages, affordances, streaming, send, respond, reset, notify }` and the `AgentChat`
  type. `convId` is a `useRef`. `notifyDataChanged()` fires after an approved write.
- `src/app/api/agent/chat/route.ts` — streaming route. `pumpLoop()` maps `LoopEvent`s to SSE
  frames; it already forwards **every** non-`proposal` event (line ~74), so `thinking`
  frames are **already on the wire**. Holds a module-level `pending: Map<token, {toolName,
  input, conversationId}>` for parked proposals; the `action` path approves/denies by token.
- `src/lib/agent/loop.ts` — `runAgent()` async-generator. `LoopEvent` already includes
  `{ type: 'thinking'; delta }`. On a gated tool call it yields ONE `proposal` and
  `return`s, abandoning any other calls in the same turn.
- `src/lib/agent/providers/anthropic.ts` — runs `thinking: { type: 'adaptive' }` at high
  effort and yields `{ type: 'thinking', delta }` from `thinking_delta`. Thinking is **not
  persisted** (pumpLoop only stores assistant `text` + tool calls).
- `src/lib/agent/tools/write.ts` — gated write tools. `updateMatchingRuleTool`,
  `reconcileTransactionsTool`, `mergeAccountsTool` each have a `preview()` producing a
  readable diff. `editTransactionMetadataTool` (gate `apply-undo`) has **no `preview`**, so
  the loop falls back to `JSON.stringify(input)` — the raw-JSON confirm card the owner saw.
- `src/lib/agent/conversations.ts` — `createConversation(title)`, `appendMessage(...)`,
  `getMessages(conversationId): StoredMessage[]`. Schema table `agentConversations` has
  `id, title, createdAt, modifiedAt`. **No list/delete helpers yet.**
- `src/lib/agent/tools/types.ts` — `Tool` with `gate: 'none' | 'confirm' | 'apply-undo'`,
  optional `preview(input, ctx)`, `run(input, ctx)`. `ToolContext` carries `db`.
- `src/lib/agent/ui.ts` — `UIAffordance` union (confirm/select/multiselect/account_picker/
  suggestions). The `confirm` kind carries `{ token, title, diff, confirmLabel }`.

**Global constraints:** Next.js 15 App Router, React 19, TypeScript, Tailwind 4. TDD where
there is real logic (`npm test` vitest; `npx tsc --noEmit` clean). Match the app's Origin
house style (tokens in `globals.css`); theme-aware (light/dark). Preserve streaming, error
surfacing (`⚠️`), affordance wiring, and `notifyDataChanged()`-on-write. Commit per

## Decisions (already made with the owner — do not re-litigate)

1. **Thinking display:** stream reasoning live, **auto-expanded while thinking, then
   auto-collapse** to a "Thought for Ns" chip when the answer text starts; re-expandable.
   Reasoning is **live-only** (not restored from server history).
2. **History source:** **server SQLite** (already persisted; it's on local disk). A history
   drawer lists past chats and reopens them. Not localStorage.
3. **New-chat control:** a **plus (+)** icon, not the refresh icon.
4. **Confirm cards:** restyle to Origin tokens **and** give `edit_transaction_metadata` a
   readable `preview`.
5. **Batch approval:** **both** — collapse multiple same-turn gated edits into ONE confirm
   card, **and** offer "Approve & don't ask again in this chat" (a per-conversation grant).

## Workstream A — Stream the thinking process (folded by default)

**Frontend-only.** `thinking` frames already arrive at the client; the hook drops them.

- **Hook (`useAgentChat`):** extend `ChatMessage` to
  `{ role, text, thinking?: string, thinkingMs?: number }`. In `consume()`:
  - On `thinking`: append `e.delta` to the current assistant message's `thinking`. If this
    is the first thinking delta of the turn, stamp a start time (a `useRef` or local var);
    `Date.now()` is fine (browser code).
  - On the first `text` delta of the turn (transition from thinking→answer): set
    `thinkingMs = now - start` on that message (so the chip can say "Thought for Ns"). If a
    turn produces thinking but no text (e.g. goes straight to a proposal), finalize
    `thinkingMs` when the `proposal`/`done` frame arrives.
  - Keep handling `done`/`tool_start` gracefully (no-op or reserved for future). Do not
    regress the existing `text`/`proposal`/`error` handling.
- **UI (`ChatPanel`):** add a `ThinkingPanel` subcomponent rendered **above** the assistant
  markdown inside the assistant bubble (or just above it), only when `message.thinking` is
  non-empty. Behavior:
  - While the message is still streaming and `text` is empty → **expanded**, showing the
    reasoning streaming in a dimmed, smaller, `whitespace-pre-wrap` (or `MarkdownMessage`)
    box with a subtle left border/`--color-border-base-subdued`, capped height with
    `overflow-y:auto`, auto-scrolled.
  - Once `text` is non-empty (answer started) → **collapse** to a chip:
    “✨ Thought for {ceil(thinkingMs/1000)}s ▸” using `--color-text-base-subdued`. Clicking
    toggles expand/collapse. Default collapsed after the answer starts.
  - Purely local `useState` for expanded/collapsed per message; derive the initial state
    from whether text has started.
- **Empty-bubble fix (owner-reported):** turns that go *thinking → tool call* (or a
  confirm-resume) emit no answer text, leaving the empty `{ role:'assistant', text:'' }`
  placeholder the hook appends on every `send`/`respond` as a **blank bubble** in the
  transcript. Fix at the render layer in `ChatPanel`: **do not render an assistant message
  whose `text` is empty** unless (a) it is the actively-streaming last message (show
  `TypingDots`), or (b) it has non-empty `thinking` (show the reasoning panel/chip). A
  stranded empty placeholder then renders nothing. (Optional secondary cleanup: have the hook
  reuse the existing trailing empty assistant placeholder on `respond` instead of appending a
  second one — but the render guard is the authoritative fix and must handle all sources.)
- **Persistence:** none. On reload / `loadConversation`, restored assistant messages have no
  `thinking` — the panel simply doesn't render. That's intended.
- **Test:** a small unit test on a pure helper `formatThoughtDuration(ms)` (e.g. `1400 →
  "1s"`, `12800 → "13s"`), plus optionally a `renderToStaticMarkup` check that a message
  with `thinking` renders the collapsed chip text. Keep it light; the streaming behavior is
  manual-verified.

## Workstream C — Chat history (server-backed)

Retrieve past conversations from SQLite and let the user reopen them.

- **Data helpers (`conversations.ts`):**
  - `listConversations(db): Promise<ConversationSummary[]>` where
    `ConversationSummary = { id, title, modifiedAt, messageCount }`, ordered by `modifiedAt`
    desc. **Title:** conversations are created with an empty title, so derive a display
    title from the **first user message** text (trimmed to ~60 chars); fall back to
    "New chat" when empty. Exclude conversations with zero user messages (abandoned empty
    shells) from the list.
  - `deleteConversation(id, db): Promise<void>` — delete the conversation and its messages.
- **API (`src/app/api/agent/conversations/route.ts`):**
  - `GET` → `{ conversations: ConversationSummary[] }`.
  - `DELETE` (body `{ id }`) → `{ ok: true }`.
  - Loading a conversation's messages reuses the existing `getMessages`; expose it as
    `GET /api/agent/conversations/[id]` → `{ messages: {role, text}[] }` (map `StoredMessage`
    to chat shape: keep `user`/`assistant` rows that have text; drop `tool` rows and
    tool-call-only assistant rows; a parked proposal on a resumed chat is out of scope —
    render text only).
- **Hook (`useAgentChat`):** add `loadConversation(id)`:
  - fetch `GET /api/agent/conversations/:id`, set `messages` to the returned transcript,
    set `convId.current = id`, clear `affordances`. Gated on `!streaming`.
- **UI:** add a **history button (clock icon)** to the `ChatPanel` header (left of new-chat).
  Clicking opens a **history view** that overlays the message area (in-panel, not a separate
  modal): a list of `ConversationSummary` rows (title + relative time + message count), each
  row opens the chat via `loadConversation`; a small trash affordance per row calls
  `DELETE` then refreshes the list. A "＋ New chat" affordance at the top. Close returns to
  the current transcript. Style with Origin tokens (`origin-card`/list rows, hover states).
- **New-chat semantics:** `reset()` stays as-is (fresh `convId`, cleared transcript). The old
  conversation remains in the DB and appears in history. No size cap (local disk).
- **Test:** unit-test `listConversations` title-derivation + empty-shell exclusion and
  `deleteConversation`, using `makeTmpDb()` and real `appendMessage`/`createConversation`.

## Workstream D — Polish the confirm / affordance cards

Two parts.

- **Restyle `Affordances.tsx`** to the Origin system (verify light + dark):
  - Card container: `origin-card` surface with `--space` padding and `--radius-3`, not
    `rounded border`.
  - Title: `heading-xsmall` / `text-small font-medium` with `--color-text-base-default`.
  - Summary + meta: `text-small` / `text-xsmall` with `--color-text-base-subdued`.
  - before/after diff: keep the mono lines but color with
    `--color-text-critical` / `--color-text-success`; "affected" in subdued text.
  - Buttons: primary action `origin-btn origin-btn-primary`, Deny/secondary
    `origin-btn origin-btn-secondary`; option/account/suggestion chips
    `origin-btn origin-btn-secondary` (small). Preserve all `respond(...)` wiring and the
    tokenless-suggestion convention.
- **Readable `edit_transaction_metadata` preview (`write.ts`):** add `preview(input, {db})`
  that looks up the transaction by `input.id` and resolves category/subcategory **display
  names** from the taxonomy, returning e.g.:
  `title: 'Recategorize transaction?'`,
  `diff.summary: '"WHOLE FOODS #123" → Healthcare / Wellness'`, and where a field is
  unchanged omit it. If the transaction is missing, return a clear summary
  (`Transaction <id> not found`). Reuse existing read helpers (transactions + taxonomy);
  do not hand-roll SQL. Keep the `apply-undo` gate.
- **Test:** unit-test the edit preview against `makeTmpDb()` with a seeded transaction +
  taxonomy — asserts the summary shows resolved names, not raw ids/JSON.

## Workstream E — Ask once for batch changes (both mechanisms)

Goal: reclassifying N transactions should not require N separate confirmations.

### E1 — One card for a same-turn batch
- **Loop (`loop.ts`):** when an assistant turn contains **more than one gated call**, collect
  them and yield a single **batch proposal** instead of returning after the first. Introduce
  a new affordance kind `confirm_batch` (in `ui.ts`):
  `{ kind: 'confirm_batch', token, title, items: { summary: string }[], confirmLabel }`.
  Build each `items[].summary` from the tool's `preview()` (reuse D's readable summaries;
  fall back to a short generic line). Run any **non-gated** calls in the turn first (as
  today), then park the whole gated batch under one token and `return`.
- **Route (`route.ts`):** the `pending` map value becomes
  `{ conversationId, calls: {token?, toolName, input}[] }` (a single parked entry may hold
  many calls). On **approve** of a batch token: run every call in order through its tool's
  `run`, `appendMessage` a `tool` result per call, then resume `pumpLoop`. On **deny**:
  append synthetic declined results for all and resume. Preserve the existing
  single-proposal path (a one-item batch behaves exactly like today).
- **System prompt nudge (`systemPrompt.ts`):** add a line encouraging the model, when
  changing several transactions the same way, to emit the edits **together in one turn** (or
  prefer `update_matching_rule` when a pattern generalizes) so they batch into one card.

### E2 — "Don't ask again in this chat" grant
- **Affordance:** the confirm and confirm_batch cards gain a third control, e.g. a primary
  split "Approve" + a secondary "Approve & don't ask again". Represent as a `scope` on the
  response: extend the client `respond(token, decision, value?, scope?: 'once' | 'always')`
  and carry `scope` in the POST body `action`.
- **Route + loop grant:** keep a module-level
  `grants: Map<conversationId, Set<toolName>>`. On approve with `scope: 'always'`, add every
  approved tool name to the conversation's grant set. When building the loop
  (`newLoop`/`runAgent` opts), pass the granted set; in `loop.ts`, a gated call whose tool
  name is granted is treated like `gate: 'none'` — **run directly** (still `snapshotDb`
  inside the tool's `run`), no proposal. Grants are per-conversation and in-memory (reset on
  server restart) — acceptable for a local app; note this in code.
- **Interaction with E1:** with a grant active, subsequent gated calls just run — no batch
  card needed. Without a grant, a multi-edit turn still collapses to one card via E1. Both
  paths must leave history well-formed (assistant(tool_use…) → tool(result…) alternation).
- **Test:** unit-test the loop with a stubbed provider that emits two gated calls in one
  turn → asserts a single `confirm_batch` with two items (E1); and a loop given a grant for a
  tool → asserts the gated call runs without yielding a proposal (E2). Drive `runAgent`
  directly with a fake provider/tool, no network.

## Suggested build order (each an independently testable commit)

1. **Workstream A (thinking)** — smallest, isolated, high perceived-latency win. Hook + UI +
   duration test.
2. **Workstream D (confirm polish)** — styling + edit preview + preview test. Independent.
3. **Workstream B + C (plus icon + history)** — helpers, endpoints, hook `loadConversation`,
   history drawer. B folds into C's commit.
4. **Workstream E (batch approval)** — loop/route/affordance/systemPrompt; the deepest
   change. E1 then E2, or together. Land last so the smaller wins aren't blocked on it.

## Testing
- `npm test` green and `npx tsc --noEmit` clean at every commit.
- Unit tests: thought-duration formatter; `listConversations`/`deleteConversation`; edit
  preview names; loop batch + grant behavior (fake provider).
- Manual (via `npm run dev`, seed with `npm run demo:seed` and point `DATABASE_URL` at
  `data/demo/demo.db`): thinking streams then collapses; **no blank bubbles remain after a
  thinking-only or confirm turn**; history drawer lists/opens/deletes; restyled confirm card
  reads cleanly in light + dark; asking to recategorize several transactions yields ONE card,
  and "don't ask again" applies the rest silently. Note what was manually verified.

## Out of scope
- Persisting reasoning/thinking to the DB; restoring thinking on reload.
- Cross-conversation or persisted (survives-restart) permission grants.
- localStorage history; history search/rename.
- Streaming provider/model changes; new tools; emoji picker; merge/PR decisions.
